Read the registry as a system.

Four documented moves explain how Gaia turns a skill from a private prompt artifact into an attributed, evidence-backed public record.

01 / 04

Attribution is the first record.

Gaia starts with a human author, not with a model claiming the result. Its README describes the registry as a place to verify a skill, check its capability, and credit the person who authored it.

That distinction is the product's north star: the skill can move through an agent ecosystem while its provenance stays attached to a developer.

Product boundary: the source explicitly says Gaia is not a marketplace or an installer.

02 / 04

Appraisal gives the skill a legible basis.

The README names nine evidence types, from an arXiv paper or repository link to peer review, benchmark results, verifier attestation, and Gaia's own fusion recipe.

Evidence is also graded: Platinum / S, Gold / A, Silver / B, Bronze / C, or Grey / ungraded. Trust Magnitude is described as the evidence grade at the skill level.

Read this as: an evidence vocabulary, not a promise that every skill has the same proof.

03 / 04

The graph makes relationships visible.

Gaia's registry is organized as a skill tree. Stars name the rank axis; named skills can sit in a wider graph, connect through paths, or emerge through a fusion.

The source README shows a fusion example where grill-me and ubiquitous-language lead to grill-with-docs. The relationship is the point: a capability can gain shape through its connections.

04 / 04

The record is meant to travel.

The registry is not only a web destination. The documented CLI can initialize a repository, scan for skills, push a submission, and open the skills explorer.

The source also documents a static read-only JSON API, named-skill and graph surfaces, badges, and a public Trust Ledger/leaderboard. These are links into Gaia's real surfaces, not integrations run by this portfolio page.

Operational boundary: this case study makes no remote API request and does not install or summon anything.

Graph design

Make capability relational.

The tree, named skills, stars, paths, and fusion model give the registry its organizing structure. The graph is how individual evidence becomes a public map rather than a loose list.

CLI

Carry the registry into a developer's repo.

The README documents the command surface around init, scan, push, tree, appraise, fuse, and skills. The CLI is the path from local skill work to a public record.

MCP server

Make the graph available to agents.

The source credits the MCP server in Marcus's documented scope. The README also documents the Agent Plugin & MCP path; this portfolio explains the role but does not reproduce or run that server.

Curation pipeline

Give evidence a governed place to land.

Evidence types, grades, named-skill review, fusion structure, and the Trust Ledger are the curation vocabulary described by the source. They make attribution more durable than a single repository page.
